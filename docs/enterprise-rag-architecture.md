# Enterprise RAG - архитектурная спецификация

Version: 1

Status: Proposed

Основа: `architecture-baseline.md`, `mvp-scope.md`, ADR-001 – ADR-005.

## Назначение

Документ определяет контракты и правила взаимодействия компонентов
Enterprise RAG до начала реализации модуля Documents,
RabbitMQ и Document Ingestion Worker.

На данном этапе проектируются загрузка и обработка
PDF, TXT, MD, векторное хранение, семантический поиск и ссылки на источники.
Генерация ответа через LLM Gateway, полноценная OIDC-аутентификация и
аудит безопасности остаются требованиями последующего развития MVP.

Описание является проектным решением, а не подтверждением того,
что все перечисленные компоненты уже реализованы.

## Архитектурные границы

Core API сохраняет архитектуру Modular Monolith на .NET 10 / ASP.NET Core.
Documents является его внутренним прикладным модулем, а не отдельным микросервисом.

- **React + TypeScript**
  предоставляет интерфейс загрузки документов,
  просмотра состояния обработки и результатов поиска.
  Клиент не принимает решений об авторизации.

- **Core API / Documents**
  регистрирует документы, управляет их версиями и метаданными,
  определяет допустимость операций, создаёт ingestion jobs и
  передаёт в retrieval доверенные ограничения доступа.

- **MinIO**
  хранит оригиналы документов в приватном S3-compatible хранилище.
  Не определяет состояние обработки и права пользователей.

- **RabbitMQ**
  доставляет сообщения о заданиях.
  Повторная доставка допустима;
  брокер не является источником истины для состояния документа.

- **Document Ingestion Worker (.NET 10)**
  извлекает и очищает текст, формирует chunks, запрашивает embeddings и сохраняет результаты.
  Имеет только необходимые технические полномочия и не изменяет ACL.

- **AI Orchestrator (Python / FastAPI)**
  вычисляет embeddings с помощью существующей модели,
  выполняет semantic retrieval и формирует контекст со ссылками на источники.
  Не устанавливает права пользователей.

- **PostgreSQL + pgvector**
  хранит документы, технические состояния, задания, Outbox, ACL, chunks и embeddings.
  Это источник истины для постоянного состояния платформы.

Синхронный HTTP используется для операций клиента и взаимодействия с AI Orchestrator.
Асинхронная доставка через RabbitMQ используется для длительной обработки документов.
Операции хранения выполняются непосредственно с PostgreSQL и MinIO через внутренние доверенные компоненты.

## Поток загрузки и обработки

1. Клиент обращается к Core API для регистрации загрузки.
   Core API проверяет допустимость операции и создаёт документ в состоянии `PENDING_UPLOAD`.

2. Клиент получает короткоживущий presigned URL и загружает файл напрямую во временную область MinIO.
   Ключ объекта создаёт сервер, а не клиент.

3. Core API после подтверждения проверяет наличие, тип, размер и контрольную сумму фактически загруженных данных.
   Подтверждённый оригинал закрепляется под неизменяемым ключом версии;
   доступ на запись по прежнему временному URL не должен позволять заменить этот оригинал.

4. После успешной проверки документ переходит в `UPLOADED`.
   Core API одной транзакцией PostgreSQL создаёт `IngestionJob`, запись Outbox и состояние `QUEUED`.

5. Фоновый publisher доставляет сообщение из Outbox в RabbitMQ.
   Запись считается опубликованной только после подтверждения брокера.

6. Worker получает сообщение, проверяет актуальность задания и атомарно захватывает его.
   После этого читает оригинал из MinIO, извлекает текст, очищает и делит его на chunks.

7. Worker запрашивает embeddings у AI Orchestrator по внутреннему HTTP-контракту, не загружая ML-модель в собственный процесс.

8. Worker сохраняет chunks и embeddings в PostgreSQL.
   Полностью проверенный набор результатов публикуется для поиска только при успешном завершении актуального задания.

9. Завершение задания `SUCCEEDED` и переход документа в `READY` фиксируются согласованно в PostgreSQL.
   Только после этого Worker подтверждает сообщение RabbitMQ (`ack`).

Общей транзакции PostgreSQL, MinIO и RabbitMQ нет.
Корректность обеспечивается проверкой подтверждённых состояний, Transactional Outbox, идемпотентностью и восстановлением после сбоев.

## Поток семантического поиска

1. Клиент отправляет вопрос в Core API.

2. Core API проверяет доверенную идентичность и допустимость операции,
   определяет разрешённую область документов
   и передаёт её по защищённому внутреннему контракту в AI Orchestrator.

3. AI Orchestrator вычисляет embedding вопроса совместимой моделью
   и выполняет параметризованный запрос к PostgreSQL + pgvector.

4. Фильтры доступа, состояния `READY`, отсутствия удаления, актуальной версии обработки
   и ревизии модели применяются **до** выбора Top-K фрагментов.

5. AI Orchestrator собирает ограниченный контекст и возвращает результаты с идентификаторами документов,
   страницами или позициями chunks и выдержками из текста.

6. Core API повторно проверяет допустимость выдачи данных перед возвратом клиенту.

Поисковый запрос к pgvector выполняет AI Orchestrator, а не Core API.
Core API остаётся владельцем решения о доступе.
Прямой публичный доступ к AI Orchestrator, chunks и объектам MinIO не предоставляется.

## Логические контракты

### Document

Основные поля:

- `DocumentId` - уникальный идентификатор документа.
- `OwnerId` - идентификатор владельца документа.
- `FileName` - исходное имя файла.
- `ContentType` - проверенный MIME-тип файла.
- `Size` - размер файла в байтах.
- `Checksum` - контрольная сумма содержимого.
- `ObjectKey` - ключ оригинала в MinIO.
- `ContentVersion` - версия содержимого документа.
- `ProcessingVersion` - версия текущей обработки.
- `ReadyProcessingVersion` - версия завершённой индексации.
- `Status` - текущее состояние документа.
- `CreatedAt` - дата и время создания.
- `UpdatedAt` - дата и время последнего изменения.
- `DeletedAt` - дата и время логического удаления.
- `ACL` - связь с правилами доступа OWNER/SHARED.

Владелец данных: модуль Documents в Core API.

Документ создаётся при регистрации загрузки.
В пределах `ContentVersion` проверенный `ObjectKey` и содержимое оригинала неизменны.
Замена файла создаёт новую версию содержимого.
Worker вправе изменять только согласованные технические состояния через проверяемый контракт.

### IngestionJob

Основные поля:

- `JobId` - уникальный идентификатор задания.
- `DocumentId` - идентификатор обрабатываемого документа.
- `ContentVersion` - версия исходного содержимого.
- `ProcessingVersion` - версия выполняемой обработки.
- `ModelId` - идентификатор модели embeddings.
- `ModelRevision` - ревизия используемой модели.
- `Status` - текущее состояние задания.
- `AttemptCount` - количество попыток обработки.
- `NextAttemptAt` - время следующей попытки.
- `LeaseUntil` - срок действия захвата задания.
- `LeaseToken` - токен защиты от устаревшего Worker.
- `LastErrorCode` - код последней ошибки.
- `CreatedAt` - дата и время создания задания.
- `UpdatedAt` - дата и время последнего изменения.
- `CorrelationId` - идентификатор для сквозной диагностики.

Владелец данных: модуль Documents в Core API.

Core API создаёт логическое задание и Outbox в одной транзакции.
Worker захватывает, продлевает и завершает задание только через атомарную проверку его состояния, версии и токена захвата.
Повторная доставка сообщения относится к тому же `JobId` и не создаёт новое логическое задание.

### DocumentChunk

Основные поля:

- `ChunkId` - уникальный идентификатор фрагмента.
- `DocumentId` - идентификатор исходного документа.
- `ContentVersion` - версия исходного содержимого.
- `ProcessingVersion` - версия обработки фрагмента.
- `Ordinal` - порядковый номер фрагмента.
- `Text` - извлечённый текст фрагмента.
- `TextChecksum` - контрольная сумма текста.
- `PageNumber` - номер страницы PDF, если определим.
- `SourceOffset` - позиция фрагмента в исходном тексте.
- `ChunkingConfigId` - идентификатор настроек разбиения.

Владелец данных: модуль Documents в Core API.

Worker создаёт и сохраняет фрагменты текущей обработки.
Комбинация `DocumentId`, `ProcessingVersion`, `Ordinal` уникальна.
Сведения об источнике должны указывать на реальное положение фрагмента в исходном документе.

### Embedding

Основные поля:

- `ChunkId` - идентификатор связанного фрагмента.
- `ModelId` - идентификатор модели embeddings.
- `ModelRevision` - точная ревизия модели.
- `Dimension` - размерность вектора.
- `Vector` - числовое векторное представление текста.
- `Normalization` - параметры нормализации вектора.

AI Orchestrator вычисляет embeddings, Worker сохраняет их в PostgreSQL.

Каждый вектор привязан к конкретному chunk и ревизии модели.
Размерность должна соответствовать модели.
Для `sentence-transformers/all-MiniLM-L6-v2` используется 384-мерное представление.
В запросе и индексе должны применяться совместимые модель, ревизия и настройки сравнения.

### SearchResult

Основные поля:

- `DocumentId` - идентификатор найденного документа.
- `ChunkId` - идентификатор найденного фрагмента.
- `ContentVersion` - версия содержимого документа.
- `ProcessingVersion` - версия индексации фрагмента.
- `Score` - оценка семантической близости.
- `Excerpt` - релевантная выдержка из текста.
- `FileName` - имя исходного документа.
- `PageNumber` - номер страницы, если определим.
- `SourceOffset` - позиция фрагмента в исходном тексте.

Результат формируется AI Orchestrator при поиске и отдельно не сохраняется.

`Score` отражает семантическую близость и не является вероятностью правильности ответа.
Выдержка и ссылка должны соответствовать одному и тому же сохранённому chunk.

### Версионирование

- `ContentVersion` - увеличивается при замене оригинала документа.
- `ProcessingVersion` - увеличивается при новой обработке, включая смену модели или правил chunking.
- `ReadyProcessingVersion` - указывает на полностью завершённую и опубликованную обработку.
- `ModelRevision` - фиксирует точную ревизию модели embeddings.

Каждое задание фиксирует версии документа, обработки и модели.

Поиск допускается только при `Status = READY` и `ReadyProcessingVersion = ProcessingVersion`.

Старые и частично обработанные chunks исключаются из результатов поиска и могут удаляться при фоновой очистке.

При повторной обработке ранее опубликованные данные остаются недоступными до успешного завершения новой индексации.

## Состояния документов и заданий

### Document

Основная последовательность: `PENDING_UPLOAD -> UPLOADED -> QUEUED -> PROCESSING -> READY`.

- `PENDING_UPLOAD -> UPLOADED`:
  Core API проверил оригинал и закрепил неизменяемую версию файла.
  Неуспешная или просроченная загрузка завершается `FAILED` либо очисткой незавершённой регистрации.

- `UPLOADED -> QUEUED`: Core API в одной транзакции создал задание и Outbox.

- `QUEUED -> PROCESSING`: Worker атомарно захватил актуальное задание.

- `PROCESSING -> READY`:
  сохранён и проверен полный набор chunks и embeddings для актуальной обработки;
  задание становится `SUCCEEDED`.

- `PROCESSING -> QUEUED`:
  временная ошибка зафиксирована, задание ожидает повторной попытки.
  До наступления срока повтора обработка не запускается.

- `PROCESSING -> FAILED`: неисправимая ошибка либо исчерпан допустимый лимит попыток.

- `READY / FAILED -> QUEUED`:
  Core API инициировал новую обработку, увеличил `ProcessingVersion` и создал новое задание с Outbox.
  При таком переходе прежний индекс закрывается для поиска.

- `UPLOADED / QUEUED / PROCESSING / READY / FAILED -> DELETING -> DELETED`:
  Core API немедленно запрещает дальнейшую выдачу документа;
  очистка оригиналов и индекса выполняется повторяемо.
  При ошибке документ остаётся `DELETING`.

Конечный статус удаления не позволяет возобновить старое задание.
Политика физического удаления должна учитывать отдельные требования хранения и аудита.

### IngestionJob

Основная последовательность: `QUEUED -> RUNNING -> SUCCEEDED`.

При временной ошибке применяется `RUNNING -> RETRY_WAIT -> QUEUED -> RUNNING`.
После исчерпания попыток либо неисправимой ошибки задание переходит в `FAILED`.

Для утративших актуальность заданий предусмотрен `SUPERSEDED`,
для заданий удаляемого документа `CANCELLED`. `SUCCEEDED`, `FAILED`, `SUPERSEDED` и `CANCELLED`
являются конечными состояниями конкретного логического задания.

Повторная попытка планируется по `NextAttemptAt` в PostgreSQL.
Исходное сообщение можно подтвердить после устойчивой фиксации состояния
и механизма повторной публикации через Outbox.
Немедленный `nack/requeue` без задержки не используется как способ планирования retry.

Lease ограничивает срок владения заданием, а `LeaseToken` служит fencing-токеном.
Просроченный или вытесненный Worker не вправе публиковать результат
даже в случае, если поздно завершил вычисления.
Recovery-процесс обнаруживает истёкшие аренды и повторно ставит актуальные задания в очередь.

## Согласованность и идемпотентность

PostgreSQL единственный источник истины для задания, состояний документа и факта завершения обработки.
Сообщение RabbitMQ содержит идентификаторы и версию схемы,
но не является основанием без проверки БД начинать индексацию или менять ACL.

Публикация Outbox допускает дубликаты:
подтверждение брокера может произойти до фиксации признака отправки в PostgreSQL.
Поэтому Worker перед обработкой сверяет `JobId`, состояние документа, `ContentVersion`, `ProcessingVersion`
и право захвата задания.

Частично сохранённые результаты привязываются к версии обработки и не становятся видимыми поиску.
Финальная публикация `READY` выполняется атомарно с подтверждением полноты данных
и завершением задания; записи старого Worker блокируются проверкой fencing-токена и актуальной версии.

Если Worker-1 завершил `Job-42` и сохранил `READY`, но упал до `ack`,
Worker-2 после повторной доставки обнаруживает `SUCCEEDED` в PostgreSQL,
не выполняет повторную индексацию и подтверждает сообщение.
При недоступности БД Worker не считает задание завершённым.

## Обработка отказов

- **Загрузка в MinIO не завершилась.**
  Документ остаётся `PENDING_UPLOAD`.
  После истечения срока временные данные удаляются
  либо загрузка завершается ошибкой; ingestion job не создаётся.

- **Файл загружен, но подтверждение в PostgreSQL не состоялось.**
  Проверяется состояние регистрации;
  временный объект можно повторно подтвердить либо удалить.
  Оригинал не становится доступным поиску автоматически.

- **RabbitMQ недоступен.**
  Задание и Outbox остаются в PostgreSQL.
  Publisher повторяет доставку после восстановления брокера.

- **Сообщение доставлено повторно.**
  Worker проверяет устойчивое состояние задания и атомарный захват.
  Завершённые или устаревшие задания повторно не индексируются.

- **Worker остановился во время обработки.**
  После истечения lease recovery-процесс организует повтор.
  Неполные результаты не открываются поиску.

- **AI Orchestrator недоступен.**
  Задание переходит в `RETRY_WAIT`, затем повторяется с ограниченной задержкой
  и числом попыток; при исчерпании лимита - `FAILED`.

- **PostgreSQL недоступен при сохранении результатов.**
  `READY` не подтверждается.
  После восстановления Worker проверяет фактическое состояние транзакции
  и безопасно повторяет необходимые операции.

- **Удаление прервалось.**
  Документ остаётся `DELETING`, его содержимое не выдаётся, очистка повторяется.

Ошибки должны регистрироваться с `CorrelationId`
и техническим кодом без раскрытия защищённого текста,
секретов и внутренних адресов во внешних ответах.

## Безопасность retrieval

В целевом MVP доверенная идентичность поступает из OIDC-compatible Identity Provider.
Решение о правах `OWNER` / `SHARED` принимает Core API.
`UserId` и список разрешённых документов переданные клиентом,
не являются доказательством доступа.

До реализации OIDC и полноценного ACL внешний поиск по корпоративным документам закрыт.
Проверка retrieval разрешается только во внутреннем изолированном тестовом окружении
с серверным фиксированным scope и явным включением тестового режима.
Режим выключен по умолчанию и не должен становиться обходным публичным API.

AI Orchestrator получает доверенный scope от Core API,
применяет его в параметризованном запросе к PostgreSQL
и выполняет фильтрацию **до Top-K**.
Обязательно исключаются неготовые, удалённые, неактуальные и несовместимые по модели данные.
Для защиты в глубину необходимы ограниченные полномочия подключения к БД;
AI Orchestrator не должен получать возможность изменять ACL.

Core API повторно проверяет допустимость выдачи результатов.
Изменение или отзыв прав должны учитываться при очередном обращении.
Логи не должны содержать полные тексты документов или поискового контекста.

Данная схема не заменяет OIDC, полноценную авторизацию
и security audit, предусмотренные общим MVP.

## Архитектурные решения и ограничения

- Сохраняется разделение .NET и Python:
  Core API и Document Ingestion Worker отвечают за прикладную логику,
  а существующий AI Orchestrator за ML-вычисления и retrieval.

- PostgreSQL + pgvector остаётся единым постоянным хранилищем платформы;
  MinIO отвечает за бинарные оригиналы,
  RabbitMQ - за доставку работы.

- Transactional Outbox необходим для согласованности создания задания и последующей публикации сообщения.
  At-least-once delivery требует идемпотентности Worker.

- Используется одна существующая SentenceTransformer-модель в Python.
  Перенос модели или дублирование inference в .NET не предусмотрены.

- Генерация LLM-ответов, LLM Gateway, Keycloak/OIDC, полный OWNER/SHARED и security audit UI
  не входят в текущую реализацию ingestion/retrieval.
  Их требования для завершения MVP сохраняются.

- Core API должен запускаться после готовности обязательной базы данных
  и миграций, не ожидая загрузки Python-модели.
  При недоступности AI Orchestrator только зависящие от него функции возвращают контролируемую ошибку.

- Для межсервисных вызовов сохраняются принятые правила таймаутов,
  отмены операций, безопасных ошибок и `X-Correlation-ID`.

- Новые микросервисы, Redis, Kubernetes, hybrid search, reranking
  и агентные сценарии не вводятся в рамках этой спецификации.

## Критерии готовности к реализации

Архитектурные контракты считаются согласованными, если:

- регистрация и подтверждение загрузки не допускают появления фиктивно готового документа;
- назначен владелец каждой сущности и определены допустимые изменения состояния;
- версии файла, обработки и модели проверяются на границах записи и поиска;
- Outbox, retry, lease и восстановление исключают потерю задания и некорректную повторную публикацию результата;
- поиск не возвращает неготовые, удалённые и неразрешённые фрагменты;
- границы Core API, .NET Worker и AI Orchestrator соответствуют утверждённой архитектуре;
- требования для реализации Documents + MinIO, RabbitMQ и Worker не содержат неразрешённых противоречий.
