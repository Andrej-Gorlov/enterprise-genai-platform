# Enterprise GenAI Platform

## 1. Цель проекта

Создать корпоративную платформу генеративного ИИ,
позволяющую сотрудникам безопасно использовать LLM
для работы с внутренней информацией и корпоративными системами.

## 2. Основные возможности

Пользователь должен иметь возможность:

- авторизоваться через корпоративную систему идентификации;
- задавать вопросы на естественном языке;
- получать ответы на основании корпоративных документов;
- видеть источники информации, использованные при формировании ответа;
- выполнять разрешённые операции через AI-агентов;
- работать только с теми данными, к которым у него есть доступ.

## 3. Источники данных

На первых этапах:

- PDF;
- DOCX;
- TXT;
- внутренний REST API;
- PostgreSQL.

В дальнейшем:

- корпоративные информационные системы;
- файловые хранилища;
- базы знаний.

## 4. Типы пользователей

Employee

Обычный пользователь платформы.

Manager

Пользователь с доступом к дополнительным корпоративным данным.

Administrator

Управляет платформой и её конфигурацией.

Security Administrator

Имеет доступ к audit-информации и настройкам безопасности.

## 5. Основные сценарии

### UC-01

Пользователь задаёт вопрос по корпоративным документам.

Система:

1. определяет пользователя;
2. определяет его права;
3. выполняет поиск только среди разрешённых документов;
4. формирует контекст;
5. вызывает LLM;
6. возвращает ответ;
7. показывает использованные источники;
8. записывает операцию в audit.

### UC-02

Пользователь просит кратко изложить документ.

Система должна проверить доступ пользователя к документу
до передачи его содержимого AI-компонентам.

### UC-03

Пользователь задаёт вопрос, требующий данных корпоративной системы.

AI-агент может вызвать разрешённый инструмент/API.

Пример:

"Какой статус проекта Alpha?"

Agent:

1. определяет необходимый tool;
2. проверяет разрешение;
3. вызывает Project API;
4. передаёт результат LLM;
5. формирует ответ.

## 6. Основные ограничения

AI не должен обходить систему авторизации.

LLM не должна самостоятельно определять права доступа.

Проверка доступа должна происходить до передачи данных модели.

Все обращения к корпоративным данным должны быть аудируемыми.

Опасные операции AI-агентов должны требовать дополнительного подтверждения.

Архитектура должна позволять использовать как внешние, так и локально размещённые LLM.

## 8. Нефункциональные требования

### 8.1 Performance

Система должна поддерживать до 500 одновременно активных пользователей.

Проектная нагрузка:

- до 10 000 зарегистрированных сотрудников;
- до 3 000 активных пользователей AI;
- до 500 одновременно активных пользователей;
- до 50 000 AI-запросов в сутки.

Для AI-запросов:

- P95 полного ответа — не более 20 секунд;
- в дальнейшем целевые значения должны уточняться
  на основании реальной статистики эксплуатации.

Для обычных API-запросов, не использующих LLM:

- P95 — не более 500 мс.

### 8.2 Availability

Платформа должна быть доступна в рабочее время организации.

Плановые технические работы допускаются преимущественно
в нерабочее время и выходные.

Отказ одного экземпляра прикладного сервиса не должен
приводить к полной недоступности платформы.

Отказ необязательного компонента не должен приводить
к полной недоступности основных функций системы.

Критические компоненты не должны иметь единственной
точки отказа.

### 8.3 Scalability

Архитектура должна позволять горизонтально масштабировать
компоненты, обрабатывающие пользовательские и AI-запросы.

Рост количества пользователей и документов не должен требовать
полного изменения архитектуры системы.

Система должна позволять увеличивать вычислительные ресурсы
отдельных наиболее нагруженных компонентов независимо друг от друга.

Целевой первоначальный масштаб:

- до 10 000 сотрудников;
- до 3 000 активных AI-пользователей;
- до 1 000 000 документов;
- до 10 000 000 фрагментов документов.

### 8.4 Security

Пользователь должен получать доступ только к данным, к которым он имеет разрешение.

Права доступа должны проверяться до передачи корпоративных данных в LLM или другой AI-компонент.

LLM не должна самостоятельно принимать решения о предоставлении пользователю доступа к данным.

AI-агенты должны иметь только явно разрешённый набор инструментов и операций.

Доступ AI-агента к корпоративной системе должен учитывать права пользователя, от имени которого выполняется операция.

Система должна предотвращать получение защищённых данных через AI-интерфейс в обход стандартных механизмов авторизации.

Использование корпоративных ограничений не должно запрещать пользователю обращаться к общим возможностям LLM, если запрос не требует доступа к закрытым корпоративным данным.

### 8.5 LLM Availability

Недоступность одного LLM-провайдера или модели не должна приводить к полной недоступности AI-функций, если доступна совместимая резервная модель.

История диалогов должна храниться внутри платформы и не должна зависеть от конкретной LLM.

При переключении на резервную модель платформа должна иметь возможность восстановить необходимый контекст разговора.

Если резервная модель недоступна, пользователь должен получить контролируемую ошибку, а не потерять историю разговора.

### 8.6 Auditability

Система должна вести аудит операций, связанных с доступом к корпоративным данным.

Audit должен позволять определить:

- кто выполнил операцию;
- когда она была выполнена;
- к каким данным был выполнен доступ;
- какой AI-сервис или агент участвовал в операции;
- какой инструмент был вызван;
- успешно ли завершилась операция.

Audit-записи не должны изменяться обычными пользователями.

Срок хранения audit-информации должен задаваться политиками организации и применимыми законодательными требованиями.

Для проекта принимается первоначальное значение: не менее 1 года.

### 8.7 Recoverability

Критические пользовательские данные должны регулярно резервироваться.

Для основных данных платформы:

- RPO <= 15 минут;
- RTO <= 1 час.

Для audit-данных:

- потеря подтверждённых audit-записей недопустима.

После отказа LLM история диалогов не должна теряться.

Процедуры восстановления должны периодически проверяться, а не существовать только в документации.

### 8.8 Data Retention

История пользовательских диалогов хранится до её удаления пользователем либо до истечения срока, определённого политикой организации.

После удаления пользователем данные переводятся в состояние soft delete.

Окончательное удаление выполняется через 30 дней, если юридические или корпоративные требования не требуют иного срока хранения.

Аналогичная политика может применяться к пользовательским документам.

Срок хранения audit-информации определяется политиками организации и законодательными требованиями.

Первоначальный проектный диапазон: от 1 до 3 лет.
